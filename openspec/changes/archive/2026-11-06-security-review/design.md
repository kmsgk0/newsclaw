# Design

## Context

现有工程规范提供通用检查表，npm 脚本与 PR workflow 已覆盖规格、文档、提交引用、密钥及依赖。产品业务尚未实现，当前可以核对文档、检查工具及其实际输出。详细需求见两份 delta spec。

## Goals / Non-Goals

使检查者能够根据产品边界准备数据、选择检查手段、判断结果并追溯证据。此次补齐文档、命令入口和现有工具的实际记录，业务运行检查继续随对应实现开展。

## Decisions

### 检查方法与评审口径

`docs/security-checks.md` 集中维护测试身份、七项检查、权限与异步数据断言、问答样例及报告落点。用产品需求编号定位尚未实现的接口，真实路由在 OpenAPI 建立后登记。保留公共内容匿名访问、用户管理本人配置与管理员管理公共资源的区别。

`docs/standards/review.md` 保留简短检查表，补充七类核查与七个评审维度。记录使用的手段、对象、规约依据、判据和结果；发现问题后给出具体修正与复测要求。

### 命令复用

完整检查使用 `npm run check`，安全检查使用 `npm run check:security`；按原命令的参数指定提交基线或附加扫描对象。文档和 PR workflow 使用相同实现，既有工具测试验证正常、失败及依赖缺失时的行为。

### 报告组织

`reports/README.md` 提供索引，`security-baseline.md` 与 `review-01.md` 分别保存当前安全基线和文档、工具审查。正文写清对象、日期、版本、检查方式、结论与证据链接，具体主题放在标题中。详细输出进入 `reports/2026-11-06-security-review/`，后续其他工作按日期和主题另建目录。

同一正式报告直接更新，历史由 Git 保存。原始输出先在本地采集，再移除凭据、本机路径和连接别名；公开证据注明处理方式，保留命令、退出码、计数与错误原因。业务自查、权限、并发及事务的报告位置在检查方案中约定，运行后再保存实际记录。

### 实施状态与入口

检查方案关联现有需求，运行日志目标补充操作人、技能、结果、耗时及实际用量的检查依据。路线图保留全部业务任务，增加必要的安全自查与复测安排。README、AGENTS、安全和测试规范提供直接入口。

## Risks / Trade-offs

- 当前工具只能检查已有仓库内容。报告明确范围，业务接口、构建产物与运行日志在形成后补查。
- 扫描输出可能包含机器信息。公开前脱敏，保留影响判断的内容，原始输出留在本地。
- 报告更新可能导致材料散落。固定入口提供当前结论，证据按一次工作归组，通过索引查阅。

## Migration Plan

先完成检查方案和评审方法，统一文档中的 npm 命令与查阅入口；执行检查并整理真实证据，核对所有文件及未完成状态。文档任务完成后同步工程规范主规格并归档，业务目标继续留在产品规划中。
