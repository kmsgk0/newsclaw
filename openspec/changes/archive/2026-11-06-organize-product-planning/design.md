# Design

## Context

产品目标按账号、新闻库、个人编辑、技能、专题和运行恢复六组组织，工程规范及评测材料分别维护在 `docs/standards/` 与 `docs/evaluation/`。本变更沿用这些内容，调整产品规划与开发入口。开发约定见 [spec.md](specs/contribution-workflow/spec.md)。

## Goals / Non-Goals

保持完整需求可查阅，使一次变更能够按自身范围完成与归档。迁移保留需求编号、场景、设计及任务中的验证方法，不调整产品功能、不新增业务实现或自动管理工具。

## Decisions

### 产品资料集中维护

| 文档 | 内容 |
| --- | --- |
| `docs/product/README.md` | 产品目标、完整功能范围、能力索引与已交付规格入口 |
| `docs/product/design.md` | 架构、数据关系、共享业务与技术取舍 |
| `docs/product/requirements/*.md` | 六组待实现的目标需求及 Scenario，保留既有编号和正文 |
| `docs/product/roadmap.md` | 建议交付顺序及尚未纳入具体变更的实施任务、验证方法 |

产品入口关联完整目标与现行规格，工程规范继续维护各领域的实施约束。六份能力文档改用普通需求章节，具体 Requirement 和 Scenario 保持原意。使用现有 Markdown 和链接维护这些关系。

### 按交付范围建立变更

路线图按运行基础、账号、异步采集、搜索与事件、编辑问答、技能、个性化阅读、专题成果、集成与运行交付组织建议顺序。实际开工时建立对应 change，选取所需需求和任务，相关页面、测试和文档随能力一起完成。

任务纳入具体变更后，路线图保留编号、摘要与链接，完成状态在变更中维护。文档或设计工作只跟踪相应材料与核对任务，业务实现与运行验证进入对应的实施变更。

### 完成与资料迁移

当前变更的任务和规定验证完成后，独立同步规格并归档。产品入口对已交付需求维护编号、摘要及现行规格链接，待实现需求继续保留完整描述。

`2026-10-28-newsclaw-foundation` 的产品内容迁入上述文档。迁移核对完成后，将基础规划变更保存在 `openspec/changes/archive/2026-10-28-newsclaw-foundation/`，保留原始需求、设计和任务状态，修正目录变化影响的相对链接。归档时跳过规格同步，未完成业务继续由产品规划及后续增量变更承接。本次文档调整完成后独立同步开发流程规格并归档。

## Migration Plan

先完整迁移六组需求，逐条核对编号及场景正文；随后迁移总体设计与任务清单，更新相对链接，并在路线图中给出交付分组。最后更新项目入口、AI 与数据规范、评测材料及 OpenSpec 配置，核对引用后归档基础规划变更，保留任务状态并跳过规格同步。

迁移以开始操作时的实际文件为依据，保留已有工程规范和其他工作成果。核对源文件内容、未完成任务、链接、完整 diff 和仓库检查结果。

## Risks / Trade-offs

目录变化会影响相对链接，迁移时统一核对所有引用。产品规划与现行规格承担不同职责，已交付需求改为引用现行规格，避免重复维护同一正文。交付分组随实际任务确定，不预先创建全部活动变更。
