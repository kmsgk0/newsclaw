# Design

## Context

NewsClaw 已有基础能力规约、五类工程规范及 OpenSpec 工作流技能。文档组织沿用现有目录，使项目介绍、行为定义、工程约束和操作方法各有明确入口。目标见 [proposal.md](proposal.md)，开发约定见 [spec.md](specs/contribution-workflow/spec.md)。

## Goals / Non-Goals

让开发者仅凭仓库文件即可找到需求、确定实施任务并执行相应检查。沿用现有 OpenSpec 工具和工程规范，提供可在本地与 PR 中运行的确定性检查。产品功能与技术合同保持不变；应用运行和业务测试由相应实现任务提供。

## Decisions

### 按用途组织文档

| 位置 | 职责 |
| --- | --- |
| `README.md` | 项目定位、功能规划、实际进度、查看与使用方法、文档索引 |
| `AGENTS.md` | 开始工作时必须遵守的开发规则，以及相关规约和规范入口 |
| `CONTRIBUTING.md` | 准备规约、按任务实施、验证、提交和归档的方法与命令 |
| `docs/standards/` | 产品、后端、安全、测试、部署运维的具体合同及检查方法 |
| `openspec/changes/` | 活动变更的目标、设计、需求场景和实施任务；已完成变更保存在归档目录 |
| `openspec/specs/` | 实现与验证完成后同步的现行规格 |
| `openspec/config.yaml`、项目技能 | 将项目要求带入规约生成及测试、发布等具体操作 |

操作步骤集中在开发指南，具体工程要求保留在对应规范。其他入口通过链接引用，避免多份文档分别维护同一套步骤。文档按其读者和用途说明目标行为、技术方案及使用条件，README 的功能规划与任务清单的实施状态保持一致。

### 用规约衔接开发工作

开始修改前，读取相关现行规格、活动变更和工程规范。已有活动变更覆盖本次内容时沿用；需要新增或改变行为时，先创建或更新对应变更，再开展实现。提案确定范围，设计说明方案与取舍，场景定义可观测结果，任务列出实现步骤及验证方法。

实现按任务依赖推进，必要的测试和文档与对应任务一起完成。产品行为或关键方案变化时先更新规约。提交按实际改动组织，说明对应变更和相关需求或任务，使记录能够追溯到开发依据。

### 按交付类型检查结果

检查同时核对需求是否落实、实际 diff 是否有规约依据。文档检查内容、链接和条款一致性；工具按自身场景检查输入、结果和失败行为；应用代码按工程规范检查业务行为与数据变化。验证方法及结果随交付说明，需保存的记录按对应任务归档。

文档通过阅读、链接与 diff 核对及 OpenSpec 严格校验验证；检查工具通过临时 Git 仓库中的真实命令与行为用例验证，workflow 使用静态检查及相同本地命令核对。项目技能保留各自的测试、发布与恢复方法，通用 OpenSpec 技能继续沿用工具提供的版本。

### 以实现和验证结果维护状态

任务在实现及规定验证完成后勾选。全部任务完成后，将变更规格同步到主规格并归档，随后检查主规格内容与严格校验结果；仍有未完成内容的变更保留活动状态。

### 自动检查入口

根目录 npm scripts 提供 `check`、`check:repo`、`check:specs`、`check:commits`、`check:security` 以及工具测试入口。本地 `check` 执行全部检查，CI 的两个任务分别执行仓库检查和安全检查；底层复用同一实现。命令失败返回非零，指出检查对象和原因。普通检查结果写到终端及 Actions 日志，专项记录按任务保存。

Node.js 标准库负责 Git、文件与进程操作，OpenSpec 负责规格校验，markdown-it 与 github-slugger 解析 Markdown 链接及 GitHub 标题锚点，Gitleaks 扫描密钥，npm 审计锁文件。依赖使用锁定版本，保持项目原有 npm 工具链。

### 文件与提交的检查范围

文档和当前文件检查覆盖 Git 已跟踪及未忽略的新文件，包含隐藏目录中的技能；本地链接和图片必须指向仓库内可纳入版本管理的目标。Markdown 锚点按 GitHub 标题规则或显式 HTML 锚点检查，代码示例与外部 URL 不参与链接解析检查。变更文件检查冲突标记和 diff 空白错误。

提交检查接受 `--base` 与 `--head`，本地默认 `main` 和 `HEAD`。以二者共同祖先为起点，只检查到 head 的非合并提交；CI 显式传入 PR 的 base 与 head SHA，避免将平台生成的合并提交当作开发者提交。文档及规格则在 GitHub 默认检出的合并结果上运行。

提交标题使用 Conventional Commits，正文用 `OpenSpec: <变更名>` 关联一个变更，并用 `Requirements: <编号列表>` 或 `Tasks: <编号列表>` 指定依据；多条 `OpenSpec:` 可以关联多个变更。检查读取该提交当时的文件树，验证提案、设计、规格和任务齐全，编号能够在所列变更中找到。活动目录和归档目录均可解析，后续补写的规格不能使此前缺少依据的提交通过。语义上的需求覆盖按 FLOW-03 对照实际内容核对。

### 安全检查与持续集成

密钥扫描覆盖所有本地可达 Git 引用的历史，以及当前已跟踪和未忽略文件的快照，输出完全脱敏；忽略的本机配置、依赖目录及临时材料不进入当前文件快照。构建产物或运行日志需要核验时，可以将实际路径传给安全检查命令。npm 审计包含开发依赖，高危或严重漏洞、扫描工具缺失以及审计服务不可用均返回非零。

workflow 在面向 `main` 的 PR 创建、更新及重新打开时执行，使用 `contents: read` 权限。`Repository checks` 安装锁定依赖后校验规格、文件、提交引用并运行工具测试；`Security checks` 安装固定版本的 Gitleaks，执行扫描、依赖审计和安全工具测试。使用 Ubuntu runner 和 Node.js 24，不调用模型服务。workflow 文件使用 actionlint 检查，下载工具校验发布包的 SHA-256。

## Risks / Trade-offs

多个入口可能出现内容不一致，因此流程集中维护、其他文档按用途引用，并在修改时核对关联入口。规约的详略按改动影响安排，文档修正写清修正内容和核对方法，工具或功能变更则明确其行为与失败条件。安全审计需要网络访问，服务不可用时保留失败结果，由执行者在连通性恢复后重新检查。
