# Design

## Context

产品规划已定义四类后台工作及按账号隔离、结果唯一和失败保留成功内容的要求。当前仓库提供产品文档和检查工具，应用尚未实现。本次完善异步执行的设计及验证依据，目标场景见 [runtime-operations](specs/runtime-operations/spec.md)。

## Goals / Non-Goals

明确从任务接收到结果提交的责任和失败处理，使后续实现能够按同一组场景验证。业务范围沿用采集整理、日报、编辑手记和更新提醒；交互问答与技能继续使用 SSE。此次仅交付文档，数据库迁移、运行配置、接口、Worker 及运行用例由后续实施变更完成。

## Decisions

### 数据库接收，队列执行

PostgreSQL 保存任务身份、归属、处理范围、状态与结果；Redis + BullMQ 管理排队、延迟重试及执行锁。API 与 Worker 共用业务模块和镜像，先运行一个 Worker、一个业务队列和一个没有自动消费者的死信队列。Redis 使用持久化卷、AOF 和 `noeviction`，具体依赖版本和时间参数在实现时确定。

任务与业务变更、待投递记录在同一事务提交，Worker 内的投递循环负责入队。直接在数据库提交后发送消息会留下投递失败的间隙，持久化待投递记录使这部分工作可以恢复。重复投递由任务身份、执行资格及业务唯一约束处理。

### 固定任务与业务边界

每类任务说明触发方式、输入范围和结果唯一性。同一次操作重放复用任务，合法的新采集批次或主动重新生成使用新的操作标识。日报与手记更新同一业务记录，较旧结果不能覆盖较新内容；专题重新生成仍保存新的成果。

查询接口只读并按账号隔离。管理员管理公共任务，私人任务由原有业务入口及调度处理。Worker 在执行及提交时核对目标和权限，避免已删除对象、停用信源或取消关注留下失效写入。

### 恢复与验证

BullMQ 承担续锁、失锁检测和重新领取，业务数据库只保存提交结果所需的执行资格。恢复时核对非终态任务与实际队列状态，补投缺失消息，已成功任务直接完成消息。可重试错误采用有上限的退避与抖动；最终失败与待投递死信记录同时保存，人工重放保留失败历史。

三条主要判据覆盖提交耗时、停止 Worker 后恢复，以及重复请求与重复投递的结果唯一性。另核对接收事务失败、结果提交失败、只读查询、权限和迟到结果，记录操作、响应、状态、数据库断言和运行观测。模型与信源使用可控替身，真实运行报告在执行后形成。

## Migration Plan

先核对 OPS-01 至 OPS-05 的新增场景与既有能力，再将设计和完整运行需求写入产品文档。路线图保留原任务编号与未完成状态，补充队列、任务接收、恢复及验证工作。同步 README、后端响应码和运维说明中的关联内容，完成文档及仓库检查后归档本变更，跳过业务主规格同步。

## Risks / Trade-offs

- 数据库与队列不能共同提交事务；待投递记录允许至少一次投递，业务结果按唯一约束及条件更新提交。
- 外部调用可能重复，验证分别记录执行次数与生效结果，不将结果唯一等同于模型只调用一次。
- 文档中的目标行为尚待运行验证；产品路线图保持未完成，已归档的基础规划和其他能力正文保留。
