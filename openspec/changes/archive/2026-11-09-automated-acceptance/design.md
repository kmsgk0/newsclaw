# Design

## Context

应用使用 Node 测试运行器及 Playwright，已有独立数据库、队列和 HTTP 替身。仓库检查通过 Git 读取当前文件与提交历史，必须支持普通 checkout 及 worktree。当前终端编排、CI 命令和报告位置分散，增加验收能力时需要共同维护这些入口。

## Goals / Non-Goals

提供宿主仅需 Docker Compose 与系统 shell 的完整验收；复用现有检查，结果准确，环境隔离，报告易读。业务修复、性能压测、监控告警和真实模型质量评测属于各自变更。

## Decisions

### 统一检查编排

在 `scripts/checks/` 维护唯一阶段定义，分为仓库、安全和应用三组。npm 单项入口、Make 完整检查及 CI 组检查调用同一实现。每阶段执行一次，首个失败后停止，未执行阶段保留状态。阶段定义包含名称、实际命令和结果采集方式；不维护另一套业务断言。应用组包含 SEC-07 用量检查，复用现有模型替身和正常、结构失败两种场景，通过 Node 测试事件报告结果。该阶段位于浏览器检查之后，全部前置检查正常时也会执行；模型已返回用量却未保存时返回失败。

### 容器环境与工作区

验收镜像包含锁定依赖、浏览器和扫描工具。轻量 shell 入口负责构建、创建独立 Compose 项目、运行和清理。普通 checkout 与 worktree 均读取其真实 Git 元数据，包含未提交的公开文件；私有配置、依赖缓存及历史验收输出不进入测试源码快照。运行副本与测试数据只属于本轮，正常服务与已有数据不参与清理。

测试使用专用配置、PostgreSQL 和 Redis，沿用现有测试对 API、Worker 与上游替身的装配。宿主无需安装 Node、npm、扫描工具或浏览器。应用运行继续使用现有 Compose 与应用镜像。

### 结果与阅读

Node 用例通过官方测试事件采集名称、位置、状态及耗时；Playwright 使用原生结构化结果和 HTML 报告。退出码决定阶段成败，缺少必要结果不能当作通过。汇总页展示执行时间、Git 提交及工作区状态、阶段结果、按业务整理的用例及需求编号。重复视口执行保留视口信息，不把用例数量表述为需求覆盖率。

HTML 沿用项目明亮页面与既定强调色，优先显示总体结论和失败信息，详情可展开。用量对照记录写入本轮 `usage-recording.json` 并作为附件，SEC-07 的失败名称和断言差异直接显示在用例明细中。异步数据来自本轮接口输出；截图和浏览器详情只引用实际生成的本轮文件。已有审查问题通过正式记录入口查阅，不被自动测试的通过状态覆盖。

### 产物与结束

每轮结果存入 `.local/verification/acceptance/<运行标识>/`，包含 `index.html`、`report.json`、阶段日志和测试附件，全部被 Git 忽略。报告可独立打开，浏览器详细报告沿用 Playwright 查看入口。运行中断和启动故障保留可取得的结果与原因；清理失败导致验收失败。正式报告不由命令自动改写。

## Verification

工具用例验证实际子进程成功、失败、未执行和报告生成，并核对转义、结果计数与附件路径。通过真实 Docker 入口运行现有完整套件，检查工作区读取、结果文件及容器清理；在浏览器检查真实报告的宽屏、窄屏、展开和筛选。必要的故障试验只针对验收工具与隔离环境。
