# NewsClaw 技术设计

## Context

NewsClaw 的产品范围见 [proposal.md](proposal.md)。系统以共享新闻库连接编辑、技能和专题，来源信息必须在检索、回答、时间线及图谱之间保持一致。个人会话、偏好和阅读记录归属用户，公共管理权限与私人数据访问分别判定。

## Goals / Non-Goals

**Goals:**

- 一套内容整理结果服务全站阅读和个人编辑，减少重复采集及模型调用。
- 在明确账号归属的基础上提供持续阅读、记忆更新和专题跟进。
- 采用模块化后端与固定任务，使前端、API、MCP 和后台复用同一业务规则。
- 保留可追溯来源、可观察失败和可复现运行方式。

**Non-Goals:**

- 多租户组织权限、通用工作流与可执行代码插件。
- 独立图数据库、跨领域知识推理和多智能体协作平台。
- 全网热度预测、自建对抗反爬系统及外部消息渠道。

## Decisions

### 1. 应用结构

前端使用 React Router、TypeScript、Tailwind CSS；后端使用 Node.js、Fastify 和 PostgreSQL。API 与后台执行器共享业务模块和镜像，按运行命令启动不同进程。Docker Compose 启动应用和数据库。

代码按账号、新闻与事件、编辑、技能、专题分模块。每个模块保留路由、业务服务和必要的数据访问边界。外部模型、信源解析与 MCP 协议在适配层处理。这个结构让用户请求和后台任务复用同一份规则，服务之间无需额外的网络调用。

### 2. 数据关系

| 对象 | 主要关系与约束 |
| --- | --- |
| 信源与报道 | 报道按信源和规范化 URL 唯一，分别保存发布时间与原文链接；同文可复用正文及派生结果 |
| 事件与图关系 | 一个事件关联多篇报道；实体与关系保存报道依据；事件归属修正后各入口读同一关系 |
| 账号与编辑 | 每个账号一位编辑，编辑配置与私人对象带所属账号标识 |
| 会话与记忆 | 会话拥有独立消息历史；明确兴趣和手动记忆优先于自动整理结果 |
| 技能 | 公共模板与个人副本分别保存，副本记录模板来源但独立修改和启停 |
| 专题与成果 | 专题关联报道、笔记与成果；成果保存生成时正文、技能和来源，分享只引用主动发布的成果快照 |
| 日报与手记 | 按所属账号与业务日期唯一；全站日报使用独立公共归属，不与个人日报混淆 |
| 提醒与任务 | 提醒按用户与新增报道唯一；任务记录状态、进度、结果及错误，业务唯一约束防止重复产出 |

正文与派生结果共享不合并报道来源。私人笔记和编辑手记不写回公共事件事实，也不作为新闻引用来源。

### 3. 新闻、检索与热点

RSS、公开 API 和网页内容进入统一报道格式。处理依次完成规范化、去重、筛选、摘要、必要翻译和索引。事件聚合使用标题、时间、实体和内容相似度；不确定的报道独立保留，管理员可修正。

关键词与向量检索使用 PostgreSQL 体系，结果均带报道标识及可引用文本。查询合并重复命中并限制返回数量，模型只读取本次相关材料。来源只有摘要时保留内容范围，不生成冒充原文的全文。

热点按最近 24 小时的独立信源数、有效报道数、最近发布时间及事件标识依次排序，保存每日统计用于趋势。此统计表示本站收录内容的近期热度。

### 4. 编辑执行

每次提问组装编辑人设、明确兴趣、相关记忆、当前阅读对象及会话历史；根据问题检索材料，并允许模型通过 MCP 查询新闻或事件。工具调用由服务端校验和执行，结果回传模型继续回答。设置明确的单次调用超时与工具轮次上限，达到上限时说明任务未完成。

接口流式返回文本、来源和必要状态。服务端根据工具和检索结果生成引用映射，禁止模型自行构造来源记录。图谱与双语输出校验结构后呈现。任务失败保留用户输入和已有成功消息，失败回答不作为完整结果供后续引用。

技能显式选择优先，自动选择只在本人启用的技能中选择一项，也允许不使用。技能说明参与本次编辑执行，工具权限仍由服务端决定。

### 5. 个性化与后台任务

个人日报使用兴趣和记忆筛选共享新闻，再生成导读。做梦整理消费上次成功位置之后的新活动，生成手记并补充自动记忆。手记、记忆更新和处理位置在同一事务提交，模型调用在事务外完成；失败后可重新处理同一批活动。

固定任务包括采集整理、日报、手记和更新提醒。已有任务库承担调度、领取和超时恢复，业务服务用唯一键保证重跑安全；不自行建设通用调度平台。任务状态为等待、执行中、成功、失败，执行中断后可识别超时任务并重新领取。自动重试有次数上限，管理员可主动重试。

相同新增报道命中多个关注项时只发一条站内提醒，后续另一篇报道仍能触发提醒。已保存的专题成果保留生成时材料，重新生成产生新的成果。主动分享先预览独立的公开快照，撤销后分享 URL 不再提供内容。

### 6. 接口与工程合同

接口、错误码、输入限制和幂等约定见 [后端规范](../../../docs/standards/backend.md)；页面及状态见 [产品规范](../../../docs/standards/product.md)；访问与输入边界见 [安全规范](../../../docs/standards/security.md)。测试按 [测试规范](../../../docs/standards/testing.md)从需求场景生成；构建和恢复按 [运维规范](../../../docs/standards/operations.md)执行。

## Risks / Trade-offs

| 情况 | 处理方式 |
| --- | --- |
| 信源正文不完整或不可达 | 保留实际取得内容、来源与失败状态，既有报道继续可读 |
| 模型输出不准确或结构无效 | 以检索材料限定引用，校验结构；失败明确提示并允许重试 |
| 事件被错误聚合 | 保留每篇报道及来源，管理员修正关联，不删除原始来源记录 |
| 后台重复领取或进程中断 | 业务唯一约束、成功处理位置与短事务保证一致，失败任务可重跑 |
| 自动偏好与用户填写冲突 | 用户明确内容优先，自动整理仅补充允许更新的记忆 |

## Migration Plan

从空数据库建立结构与约束，先完成可启动骨架及健康检查，再按任务依赖交付各组能力。每组使用固定样本与模型替身验证，最后核验真实模型效果。发布记录使用版本号，数据库结构变更与应用版本相配套；恢复步骤、备份目标及实际验证方法见运维规范。
