# contribution-workflow Specification

## Purpose

规定 NewsClaw 仓库文档与开发工作的衔接方式，使开发者能够找到需求和工程规范，在实施前明确变更内容，按任务完成开发与验证，并通过提交和归档维护可追溯的项目记录。本地与持续集成提供一致的自动检查，反馈文档、规格、提交引用、密钥和依赖问题。

## Requirements

### Requirement: FLOW-01 开发前准备规约与文档依据

所有仓库修改 MUST 纳入 OpenSpec，包括业务代码、页面、工具、依赖、配置、CI、文档和工程规范。开发者能够从 README 和文档导航找到产品范围、现行架构、能力规格、活动变更及工程规范。已交付行为由现行规格维护，活动变更保存未交付目标和本轮实施安排；实施前准备覆盖该范围的提案、设计、需求场景和任务，沿用已有需求编号，内容详略与实际影响相称。已有活动变更覆盖本次内容时沿用，需要变化时更新。

#### Scenario: 从仓库进入开发

- **GIVEN** 开发者已取得 NewsClaw 仓库
- **WHEN** 从 README 阅读本次工作相关的文档
- **THEN** 能找到需求与实施状态、适用工程规范和开发方法，相关本地链接均指向仓库内有效文件

#### Scenario: 新增检查工具

- **GIVEN** 计划新增检查工具，已有规约未覆盖其行为
- **WHEN** 准备实现该工具
- **THEN** 先完成对应变更的提案、设计、输入与结果场景、失败场景和实施任务，再开始实现

#### Scenario: 修正文档

- **GIVEN** 计划修正文档中的错误说明
- **WHEN** 准备对应规约
- **THEN** 写清修正内容及核对方法；仍覆盖本次内容的活动变更可以沿用

#### Scenario: 查阅完整产品规划

- **GIVEN** 产品包含已确定但尚未实现的能力
- **WHEN** 开发者从文档导航查看需求、架构和相关变更
- **THEN** 能找到全部目标及其场景、验证要求和实施安排，未实现能力保持计划状态

#### Scenario: 组织一次增量变更

- **GIVEN** 已有明确需求与后续目标
- **WHEN** 准备实施一个明确的交付范围
- **THEN** 当前变更只包含该范围的实现、测试和文档任务，其余已确认目标和验证要求仍可从文档入口找到，并保持真实状态

#### Scenario: 调整产品文档位置

- **GIVEN** 需求、设计和实施安排需要调整目录
- **WHEN** 完成文档迁移与入口更新
- **THEN** 需求编号、场景内容、设计依据及验证要求完整保留，相关链接有效，任务状态不因迁移改变

### Requirement: FLOW-02 按规约推进实施

开发者 MUST 按相关需求场景和任务实施，同步必要的测试与文档，保留既定功能。需求不清或产品行为、共享接口、关键方案发生重要变化时，先讨论并更新规约，再按明确的方案实施。普通实现细节和工作组织由开发者自行安排。

#### Scenario: 实施明确的任务

- **GIVEN** 任务范围、方案和验证方式已明确
- **WHEN** 开发者实施任务
- **THEN** 按依赖顺序完成对应修改、测试和文档，实际行为与需求场景一致

#### Scenario: 需求发生变化

- **GIVEN** 开发中发现需要改变原定产品行为或关键方案
- **WHEN** 准备采用新方案
- **THEN** 先明确变更内容并更新相关规约，后续实现与更新后的范围和场景一致

### Requirement: FLOW-03 对照需求验证实际结果

开发者 MUST 核对规约要求是否落实，以及实际改动是否符合规约和工程规范，并执行与改动相关的检查。文档核对内容、链接和一致性，工具及应用实现验证相应行为。检查结果说明对象、方法、预期和实际结果；失败或未执行的检查不能记为通过。

#### Scenario: 完成变更检查

- **GIVEN** 本次修改已完成
- **WHEN** 对照需求场景和实际 diff 检查交付
- **THEN** 每项改动有规约依据，相关需求有对应产物和验证结果，发现的遗漏得到补齐或修正

#### Scenario: 必要检查未通过

- **GIVEN** 必要检查无法执行，或实际结果不符合需求场景
- **WHEN** 整理验证结果
- **THEN** 记录具体原因或差异，保留相关任务未完成，后续按需求修正并补验

### Requirement: FLOW-04 提交记录能够追溯规约

提交 MUST 使用 Conventional Commits，说明实际改动、对应 OpenSpec 变更及相关需求或任务。提交内容与说明一致，使开发者能够从记录找到改动依据和相应产物。

#### Scenario: 查看提交依据

- **GIVEN** 一项仓库修改已经提交
- **WHEN** 开发者阅读提交说明并查看对应变更
- **THEN** 能确定修改的内容、规约依据及涉及的需求或任务，并与实际 diff 对照

### Requirement: FLOW-05 完成后同步规格与归档

任务 MUST 在对应实现及规定验证完成后勾选。变更的全部任务完成后同步主规格并归档，随后核对主规格内容并运行严格校验。归档只同步本轮已实现并验证的范围。文档导航关联能力规格与相关变更，完成状态在变更任务中维护。已交付需求正文由现行规格维护，后续目标保存在对应变更中。继续实施的变更仍有未完成内容时保持活动状态。规划内容已由后续变更完整承接时，原规划变更可保留任务状态归档，跳过未实现规格的同步。

#### Scenario: 变更完成

- **GIVEN** 变更的实现及规定验证均已完成，任务清单与实际结果一致
- **WHEN** 整理变更
- **THEN** 将已实现并验证的规格同步到主规格，保存归档材料，主规格及变更通过严格校验

#### Scenario: 仍有未完成内容

- **GIVEN** 变更仍在实施且仅完成部分实现或验证
- **WHEN** 更新项目文档与任务状态
- **THEN** 已完成任务与剩余任务清楚区分，变更保持活动状态，项目介绍不将剩余目标写成已实现功能

#### Scenario: 产品仍有后续能力

- **GIVEN** 当前变更已完成实现与验证，已有未纳入本轮的后续能力
- **WHEN** 同步并归档当前变更
- **THEN** 已完成范围进入现行规格，文档导航提供相应链接，其他能力在对应变更中保持计划状态

#### Scenario: 归档已由产品文档承接的规划

- **GIVEN** 原规划的需求、设计与未完成任务已有完整保存，文档入口已关联承接这些内容的后续变更
- **WHEN** 归档原规划变更
- **THEN** 保留原始材料与任务状态，修正归档后的链接，跳过未实现规格的同步，完整需求和后续安排仍可从文档入口查阅

### Requirement: FLOW-06 本地与 PR 使用一致的检查入口

仓库 MUST 使用单一阶段清单编排仓库、安全和应用检查，npm、Make、容器验收与面向 main 的 PR 检查复用该清单。每阶段只执行一次，任一失败返回非零并停止后续阶段。应用检查使用隔离数据库、队列和外部替身，仓库与安全检查无需业务服务或模型调用。

#### Scenario: 检查仓库变更

- **GIVEN** 仓库依赖和检查工具已准备好
- **WHEN** 在本地执行统一入口，或 PR 触发 workflow
- **THEN** 执行规定的规格、文件、提交和安全检查，输出各项结果，失败检查不能报告成功

#### Scenario: 完整应用检查

- **GIVEN** 运行条件已准备好
- **WHEN** 执行完整检查或容器验收
- **THEN** 同一清单中的规格、文件、提交、安全、工具、静态、类型、应用、接口、构建和浏览器检查各执行一次，失败后剩余阶段标记为未执行

#### Scenario: 默认检查模型调用用量

- **GIVEN** 隔离环境可通过本地模型替身复现成功回答和结构校验失败
- **WHEN** 执行完整检查、容器验收或 CI 应用检查组
- **THEN** 默认执行 SEC-07 的正常与失败对照，检查日志及消息保存的模型用量；任一不符合判据时阶段失败并返回非零，无需额外手动启用

#### Scenario: 执行单项或 CI 分组

- **GIVEN** 开发者选择一个检查或 PR 触发相应检查组
- **WHEN** 执行 npm 单项入口或 CI
- **THEN** 使用完整清单内同一实现，保留相同结果判定，仓库、安全与应用在 CI 中分别显示

#### Scenario: 检查 PR 的合并结果

- **GIVEN** 一个可以合并到 main 的 PR
- **WHEN** workflow 运行
- **THEN** 在合并结果上检查文件和规格，提交引用检查仅覆盖该 PR 的开发者提交，平台生成的合并提交不参与提交格式检查

### Requirement: FLOW-07 检查规格与仓库文件

仓库检查 MUST 执行 OpenSpec 严格校验，检查已跟踪和未忽略文件中的冲突标记、变更中的空白错误及 Markdown 本地链接、图片和标题锚点。链接目标必须属于当前仓库且可纳入版本管理；隐藏目录中的文档同样检查，代码示例和外部 URL 不作为本地链接检查。

#### Scenario: 文档和规格有效

- **GIVEN** 规格符合 OpenSpec 格式，本地链接及锚点均有效
- **WHEN** 执行仓库检查
- **THEN** 检查通过，代码示例里的链接文本不产生误报

#### Scenario: 文件或规格无效

- **GIVEN** 文档存在断链、无效锚点或仓库外目标，或改动含冲突标记、空白错误，或规格缺少必要场景
- **WHEN** 执行仓库检查
- **THEN** 返回非零并指出问题文件或规格，修正后同一入口可以通过

### Requirement: FLOW-08 验证提交的规约引用

提交检查 MUST 以指定 base 与 head 的共同祖先确定范围，核对范围内非合并提交的 Conventional Commits 标题、OpenSpec 变更引用及需求或任务编号。所引用变更在该提交中必须已有提案、设计、规格及任务；支持活动变更和已归档变更。无效基线、缺失变更、缺失文件或不存在的编号均返回失败。

#### Scenario: 规约与实施分别提交

- **GIVEN** 先提交完整规约，后续提交实现，两笔提交都引用有效变更和编号
- **WHEN** 对这段提交范围执行检查
- **THEN** 两笔提交均通过，规约提交中的任务可以保持未完成

#### Scenario: 引用归档变更

- **GIVEN** 变更已归档，提交说明仍使用原变更名
- **WHEN** 检查该提交的规约引用
- **THEN** 能在提交当时的归档目录找到变更并核对编号

#### Scenario: 引用缺失或事后补写

- **GIVEN** 提交没有规约引用、引用无效编号，或所需规约仅在后续提交中补齐
- **WHEN** 检查提交范围
- **THEN** 对原问题提交返回失败并指出缺失或无效的依据

### Requirement: FLOW-09 扫描密钥并保护输出

安全检查 MUST 使用 Gitleaks 扫描可达 Git 历史和当前已跟踪及未忽略的文件，报告启用完全脱敏。需要检查构建产物或日志时支持传入额外路径。命中密钥、工具不可用或指定路径不存在时返回非零；被忽略的本地配置不进入默认当前文件扫描。

#### Scenario: 当前或历史文件含密钥

- **GIVEN** 当前文件含合成测试密钥，或该密钥已提交后又删除
- **WHEN** 执行安全检查
- **THEN** 对相应范围报告失败，输出不包含密钥明文

#### Scenario: 默认范围与额外路径

- **GIVEN** 本地配置被 Git 忽略，另有需要检查的构建产物
- **WHEN** 执行默认扫描，随后显式传入构建产物路径
- **THEN** 默认扫描不读取忽略配置，显式传入的产物被检查，路径不存在时明确失败

### Requirement: FLOW-10 审计锁定依赖

安全检查 MUST 对锁文件内全部依赖执行 npm 审计，包含开发依赖，并输出实际漏洞信息。高危或严重漏洞返回失败；审计服务不可用或命令执行失败时明确报错。

#### Scenario: 审计结果按严重程度判定

- **GIVEN** 项目已有有效锁文件且审计服务可用
- **WHEN** 运行依赖审计
- **THEN** 输出审计结果，高危及严重漏洞导致非零退出，其他等级按实际结果显示

#### Scenario: 审计不可用

- **GIVEN** 审计服务不可达或审计命令无法执行
- **WHEN** 运行安全检查
- **THEN** 返回非零并指出审计未完成

### Requirement: FLOW-11 Docker 一键验收

仓库 SHALL 提供基于 Docker Compose 和系统 shell 的单条验收入口，在验收镜像中提供所需工具并自动准备隔离配置和服务。验收包含当前工作区的公开文件及真实 Git 历史，兼容普通 checkout 与 worktree，不要求宿主安装语言运行时和测试工具。

#### Scenario: 从工作区执行

- **GIVEN** Docker Compose 可用，仓库和镜像下载所需网络可用
- **WHEN** 从普通 checkout 或 worktree 执行验收入口
- **THEN** 构建验收镜像，运行当前公开文件的全部检查，使用专用数据库与队列和已有模型替身，结束后提供本轮报告位置

#### Scenario: 保护运行环境

- **GIVEN** 开发服务、用户配置及历史报告已经存在
- **WHEN** 验收创建和清理自身环境
- **THEN** 测试仅操作自己的容器、卷和运行副本，保留正常服务、私有配置和已有报告，不调用真实模型

#### Scenario: 失败与中断

- **GIVEN** 构建、启动、检查或清理失败，或运行被中断
- **WHEN** 结束本轮验收
- **THEN** 返回非零，保存失败阶段与可取得的结果，后续未执行检查不能标记通过，并清理本轮已创建的测试资源

### Requirement: FLOW-12 安全门禁覆盖应用反例

`make check-security` MUST 执行既有密钥、依赖、检查工具和可重现的应用安全反例，包括 SQL 注入、来源与单次 CSRF token、请求审计和浏览器标题 XSS。PR 安全任务 MUST 使用隔离 PostgreSQL、Redis、外部服务替身及 Chromium，运行同一门禁；任一检查失败返回非零。独立仓库安全扫描命令仍可无需业务服务执行。

#### Scenario: 安全门禁通过

- **GIVEN** 扫描工具、浏览器及隔离数据库和队列可用，安全反例满足预期。
- **WHEN** 开发者或 PR 安全任务运行 `make check-security`。
- **THEN** 密钥、依赖、工具、HTTP 和浏览器反例均执行，全部通过时返回零。

#### Scenario: 安全反例失败

- **GIVEN** 注入反例被放行、token 重放成功或扫描发现高危漏洞。
- **WHEN** 运行安全门禁。
- **THEN** 对应检查及门禁返回非零，不将失败记录为通过。

#### Scenario: 安全门禁缺少隔离依赖

- **GIVEN** 数据库、队列或浏览器缺失。
- **WHEN** 运行安全门禁。
- **THEN** 实际依赖失败明确报告并返回非零，不跳过应用反例。

#### Scenario: main 推送与 PR 使用同一安全门禁

- **GIVEN** 变更推送到 main 或创建面向 main 的 PR。
- **WHEN** CI 运行对应 workflow。
- **THEN** 仓库、应用和安全检查都运行，安全任务使用 `make check-security`；提交检查使用事件中实际 base 和 head。

### Requirement: FLOW-13 门禁后的镜像构建

CI SHALL 在应用、仓库和安全检查通过后构建生产镜像，并以对应提交标识标记；检查失败时不得运行后续构建。实际远端执行与分支保护须以运行记录为准。

#### Scenario: 推送后构建

- **GIVEN** 目标分支发生推送或收到合并请求。
- **WHEN** 应用、仓库和安全检查均通过。
- **THEN** CI 构建以该次提交标识标记的生产镜像，并保留构建日志。
