# 异步响应与任务状态

检查日期：2026-11-09。依据 OPS-02 至 OPS-04，使用真实 API、PostgreSQL、Redis 和 Worker；上游采用可控制等待时间的 HTTP 服务。版本与环境见[报告索引](README.md)。

## 接收响应

分别设置上游单次等待为 200 毫秒、600 毫秒，每档提交 20 个不同操作标识。40 个请求均返回 `202`，正文包含 `taskId`、`status`、`statusUrl`，不含业务生成结果。同一处理器的完整执行时间单独测量。

| 上游单次等待 | 请求数 | 提交 P95 | 完整处理时间 | P95 占处理时间 |
| --- | --- | --- | --- | --- |
| 200 毫秒 | 20 | 8.20 毫秒 | 489.65 毫秒 | 1.68% |
| 600 毫秒 | 20 | 5.25 毫秒 | 1,275.99 毫秒 | 0.41% |

判据为提交 P95 小于完整处理时间的 50%；较慢档 P95 小于较快档两倍与 100 毫秒中的较大值。两档均符合，接收请求无需等待模型和业务处理完成。

## 队列与执行观察

停止消费者后提交采集任务，确认任务和 outbox 已保存，再单独投递至队列并启动消费者。下表为同一任务的状态与队列实际计数。

| 观察点 | 任务状态 | waiting | active | completed | failed | 任务执行次数 |
| --- | --- | --- | --- | --- | --- | --- |
| 已接收，尚未投递 | pending | 0 | 0 | 0 | 0 | 0 |
| 已投递，消费者停止 | pending | 1 | 0 | 0 | 0 | 0 |
| 消费者执行中 | running | 0 | 1 | 0 | 0 | 1 |
| 采集任务已完成 | succeeded | 0 | 1 | 1 | 0 | 1 |

采集执行耗时 278.85 毫秒。最后一行的 active 为采集后产生的通知任务；采集任务自身已经成功。

另以持续依赖失败检查三次尝试上限。每次耗时分别为 129.12、131.23、142.32 毫秒，结果依次为 retry、retry、failed。最终任务为 failed、执行次数为 3，业务队列 failed 为 1、死信队列 waiting 为 1。

## 重复投递与中断

六个同操作请求并发接收，只建立一个任务和一条新闻。成功后再次投递，新闻仍为一条，模型调用仍为两次。在业务结果提交后、队列确认前终止 Worker，再启动后任务和队列均完成，新闻与模型调用数量不变。接收事务故障返回 500，孤儿任务为零。

```sh
npm run test:api
```
