# 部署运维规范

## 构建与配置

Dockerfile、Compose、依赖锁文件和无密钥的配置示例进入版本管理。使用提交或版本标识标记镜像，同一构建产物通过配置适配开发、测试与部署环境；数据库使用持久化卷。

实现后 README 应使新成员按克隆、填配置、一条命令启动和检查健康的步骤完成运行，写清所需 Node.js 与 Docker 版本、端口和必需配置。部署前核对实际锁定版本，不能把未经运行的示例写成已验证命令。

初始化只建立必要数据库结构和管理入口，不在公开配置中预置真实凭据。应用必需配置缺失时启动失败；部分内容处理失败通过任务状态呈现，不抹去已有新闻。

## 健康与日志

免认证 `/health` 返回版本、时间、就绪状态及必要依赖状态；数据库不可用时返回非成功状态。另设 `/live` 表示进程存活。健康检查不输出地址、密码或令牌，不通过付费模型生成请求检查连通性。

日志每行一个 JSON，包含 `timestamp`、`level`、`module`、`requestId` 或 `taskId`、结果及必要耗时。一次请求关联查询、模型和工具调用；后台运行能定位到对应任务。记录模型用量和调用结果，不记录完整私人问答及机密。

收到停止信号后停止接收新请求及领取新任务，等待在途工作结束；超过配置的停止期限则记录中断状态，后续按任务恢复合同重试。

## 发布与回滚

发布步骤及检查使用 [newsclaw-release](../../.agents/skills/newsclaw-release/SKILL.md)。流程为构建镜像、备份受影响数据、执行数据库迁移、启动新版本、健康检查和主流程验证，记录版本、验证结果及时间。

迁移按结构依赖顺序执行，数据库约束与应用版本配套。删除性变更单独核对数据保留需要，禁止用清空数据掩盖迁移失败。发布前保留上一可运行版本；失败时按迁移是否改变数据，选择回退应用或恢复对应数据后再启动旧版本。

从当前和上一版本分别启动一次，记录回滚步骤及实际耗时。只有真实运行过的步骤才记为演练完成。

## 备份与恢复

初始部署每日备份，保留最近 7 份；恢复目标为最多损失一天数据、两小时内恢复。备份存放在独立于业务数据卷的位置，限制访问，备份不进入 Git。

在隔离数据库上实际恢复，核对记录数量、关键关联、账号访问和新闻读取。恢复结果以演练证据确认，目标值不代表已经达到。运行规模变化后根据实际需要调整频率和目标。

## 检查

从干净环境按 README 启动，核对配置缺失、数据库断开、健康状态及停止行为。检查同一请求或任务的日志可串联，确认中断任务恢复后业务结果不重复。版本回退与备份恢复分别实际验证，失败先定位原因，不以重复发布覆盖未知故障。
