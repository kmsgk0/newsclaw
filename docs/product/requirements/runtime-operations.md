# runtime-operations specification

## Purpose

规定 NewsClaw 可复现启动、后台任务、错误处理、运行记录和恢复的可观察行为，让新闻处理与个人内容生成在失败时保持明确状态，并使开发者能够依据同一组需求验证、部署和恢复系统。

## Requirements

### Requirement: OPS-01 配置、启动与健康检查

系统 SHALL 使用 Dockerfile、Compose、依赖锁文件和无密钥配置示例支持按文档从零启动应用及必要依赖。必需配置缺失必须启动失败。免认证的 `/health` 返回版本、时间和必要依赖连通状态，独立存活检查反映进程存活；模型连接诊断不得发送付费生成请求。

#### Scenario: 按文档启动
- **GIVEN** 使用者取得仓库、准备文档规定的环境并填入必要配置。
- **WHEN** 使用者执行文档中的一条启动命令。
- **THEN** API、Worker、PostgreSQL 和 Redis 启动，API 与 Worker 使用同一镜像的不同启动命令，数据库与 Redis 数据卷持久化，匿名访问 `/health` 可取得版本、时间和依赖状态，无需额外口头步骤。

#### Scenario: 必需配置缺失
- **GIVEN** 一个必需配置项未填写或格式无效。
- **WHEN** 应用尝试启动。
- **THEN** 启动明确失败并指出配置项名称，不输出密钥值，不用隐式默认值继续运行。

#### Scenario: 数据库未就绪
- **GIVEN** 应用进程仍在运行，但数据库不可达。
- **WHEN** 运行环境查询存活与健康状态。
- **THEN** 存活检查仍反映进程状态，健康检查报告依赖未就绪并返回失败状态，不把故障伪装为健康。

#### Scenario: Redis 暂不可用时明确状态
- **GIVEN** PostgreSQL 可用而 Redis 暂时不可达。
- **WHEN** 查询健康接口并提交一个合法后台任务。
- **THEN** 健康接口报告队列依赖未就绪，API 进程仍存活；任务接收可在 PostgreSQL 持久提交后返回 `202` 并保持待投递，不能宣称已开始执行。

### Requirement: OPS-02 后台任务状态与重复执行

系统 SHALL 统一管理采集整理、日报、编辑手记和更新提醒任务。主动触发在持久接收后返回 `202`、任务标识和只读查询地址，不等待业务执行。任务记录归属、操作标识、输入引用、`pending/running/succeeded/failed`、执行次数、结果和失败原因；重复请求复用相同操作，私人任务按账号隔离，管理员仅管理公共任务。任务设置明确超时，中断可恢复，自动重试有上限，最终失败保留死信；重复执行及迟到结果不能重复生效或覆盖较新结果。

#### Scenario: 任务成功及重复触发
- **GIVEN** 有待执行的合法任务，所需外部服务可用。
- **WHEN** 执行器领取任务并完成处理，随后相同业务任务再次触发。
- **THEN** 状态按待执行、执行中、成功变化，重复触发遵守各能力的唯一性规则，不产生重复业务结果。

#### Scenario: 外部调用失败
- **GIVEN** 执行中的任务遇到模型或信源故障。
- **WHEN** 执行器结束本次尝试。
- **THEN** 任务保存具体错误；可重试且尚有额度时回到待处理并安排退避，否则标记最终失败并登记死信。原有成功内容保留，管理员可区分公共任务的未完成步骤并重试，不能读取私人任务的材料，不进行无上限自动重试。

#### Scenario: 执行器中断后的恢复
- **GIVEN** 某任务在执行中发生进程中断，队列已判定其执行锁失效。
- **WHEN** 执行器恢复并检查未完成任务。
- **THEN** 系统重新领取未完成任务并增加本次执行记录，原执行标识不能提交结果；已成功的任务直接完成消息，未完成任务沿业务唯一键写入，不重复提交既有结果。

#### Scenario: 队列恢复后的任务核对
- **GIVEN** 数据库保留未完成任务，队列恢复后部分消息缺失。
- **WHEN** Worker 核对未完成任务与队列状态。
- **THEN** 仍在等待或执行的消息继续沿用，队列已失败的任务记录失败，缺失消息重新登记投递；已成功任务不重新执行业务。

#### Scenario: 越权或缺失任务操作
- **GIVEN** 普通用户尝试重新执行公共管理任务，或者管理员指定的任务不存在。
- **WHEN** 系统接收重试请求。
- **THEN** 系统分别返回无权限或资源不存在，不创建替代任务，不修改其他任务。

#### Scenario: 接收耗时任务并只读查询
- **GIVEN** 管理员有权触发启用信源的采集，信源与模型处理需要等待。
- **WHEN** 管理员提交合法任务，随后反复读取返回的任务查询地址。
- **THEN** 提交在数据库接收事务提交后返回 `202`、`taskId`、`status`、`statusUrl`，不包含新生成结果；查询只读取任务，不增加任务数量、执行次数或模型调用。

#### Scenario: 同一操作重放与参数冲突
- **GIVEN** 一个账号已用某操作标识提交任务。
- **WHEN** 该账号再次提交相同操作标识，先使用相同参数，再使用不同参数。
- **THEN** 相同参数返回原任务及其当前状态，不产生新任务；不同参数返回 `409` 且原任务不变，其他账号不能据此读取该任务。

#### Scenario: 私人任务及结果按账号隔离
- **GIVEN** 用户 A 拥有个人日报任务，用户 B 和管理员不拥有该任务。
- **WHEN** A 查询自己的任务，B 或管理员查询同一任务，或者未登录调用方请求它。
- **THEN** A 可取得自己的状态及结果引用；跨账号与不存在任务均返回 `404`，未登录返回 `401`，响应和日志不向调用方披露私人输入或结果。

#### Scenario: 执行时目标或权限已变化
- **GIVEN** 任务已接收但尚未提交结果，目标对象被删除、信源被停用、执行主体已失去相应权限或关注被取消。
- **WHEN** Worker 开始执行或准备提交业务结果。
- **THEN** 系统重新核对当前对象和权限，拒绝不再合法的操作；提醒只针对仍有效的关注产生，不因历史任务新增已取消关注的提醒。

#### Scenario: 停止全部消费者后仍能接收
- **GIVEN** API、数据库和 Redis 可用，所有 Worker 均已停止。
- **WHEN** 提交合法任务、查询状态，再恢复 Worker。
- **THEN** 提交仍返回 `202`，任务保持 `pending`；恢复后自动投递并执行到终态，无须用户重新提交。

#### Scenario: 确认前中断与重复投递
- **GIVEN** 一个任务已提交业务结果和成功状态，但 Worker 尚未向队列完成处理。
- **WHEN** 终止 Worker 后恢复，或者人为重复投递同一任务与代次。
- **THEN** 新消费者识别数据库中的成功状态，沿用原结果且不再调用模型；数据库中只有符合业务唯一规则的一份生效结果。

#### Scenario: 旧尝试迟到不能覆盖新结果
- **GIVEN** 一个旧尝试失去执行资格后返回外部结果，任务已被新的尝试领取或同一日报已有更新版本提交。
- **WHEN** 旧尝试提交其结果。
- **THEN** 执行标识及业务版本条件阻止旧写入，不覆盖新任务状态、日报或处理位置；外部调用次数如实记录，不宣称模型只调用了一次。

#### Scenario: 有限退避重试
- **GIVEN** 模型或信源出现超时、限流或临时服务故障，任务尚有自动尝试额度。
- **WHEN** 任务处理本次失败。
- **THEN** 保存错误与次数，按指数退避及抖动重新等待；中断后的业务重领也计入总尝试，不能通过不断重投绕过上限。

#### Scenario: 最终失败可靠进入死信
- **GIVEN** 任务遇到不可重试错误或已耗尽自动尝试额度。
- **WHEN** Worker 处理最终失败，且可能在死信投递前退出或遇到 Redis 故障。
- **THEN** 数据库同时保存 `failed`、脱敏错误与待投递死信记录，恢复后该代次进入死信队列；无自动死信消费者，failed 集合与死信数量分别可查，原成功业务结果保留。

#### Scenario: 公共死信的人工重放
- **GIVEN** 公共任务已最终失败，管理员修正原因且仍有权执行。
- **WHEN** 管理员提交重试请求并重复发送同一个请求。
- **THEN** 同一任务只新增一个投递代次和一轮有限尝试额度，保留原失败记录；旧代次消息不执行，普通用户重试被拒，成功后不重复创建已有业务结果。

### Requirement: OPS-03 统一错误与事务边界

系统 SHALL 将业务变更、任务接收和待投递记录放入同一数据库事务，提交后可靠投递至消息队列。系统 SHALL 为 JSON 业务响应使用 `code`、`message`、`data`、`requestId`，成功业务码为 `OK`，失败使用登记的业务码及匹配的 HTTP 状态。流式接口通过事件提供同等错误信息。外部模型、网络及文件处理在数据库事务之外完成，成功结果使用短事务写入，失败不能提交不完整业务状态。

#### Scenario: 参数校验失败返回明确错误
- **GIVEN** 请求包含不支持的状态、非法筛选字段或类型错误的参数。
- **WHEN** 接口边界校验请求。
- **THEN** 系统返回登记的参数错误、可读信息及请求标识，不执行后续业务写入，也不退化为默认成功操作。

#### Scenario: 外部结果成功但提交失败
- **GIVEN** 某任务已取得外部结果，但数据库事务提交失败。
- **WHEN** 系统处理该结果。
- **THEN** 系统报告失败，不推进对应业务处理位置，不保留半份成果；原成功数据不被覆盖。

#### Scenario: 接收事务失败不留下半份任务
- **GIVEN** 本次业务变更需要同时登记任务与待投递记录。
- **WHEN** 在三者任一写入处注入数据库错误并回滚。
- **THEN** 本次业务变更、任务和待投递记录均不生效，不向队列投递消息，不返回 `202`。

#### Scenario: 入队前后中断可恢复
- **GIVEN** 数据库已提交业务任务与待投递记录。
- **WHEN** Redis 不可用，或投递成功后、标记已投递前进程中断，随后恢复 Worker 与 Redis。
- **THEN** 未完成投递会继续执行，允许消息重复但不遗失任务、不形成无业务关联的孤儿任务；重复消息遵守 OPS-02 的结果去重规则。

#### Scenario: 流式错误可关联请求
- **GIVEN** 一次编辑回答已经开始流式返回，随后依赖调用失败。
- **WHEN** 系统发送终止错误事件。
- **THEN** 事件包含与该请求一致的标识、业务错误与可读提示，前端标记未完成，后台能够定位对应失败。

### Requirement: OPS-04 运行记录与行为验证

系统 SHALL 使用单行 JSON 日志记录时间、级别、模块、请求或任务标识、结果及必要耗时，使请求和工具调用可以关联。日志不得包含密码、令牌或私人问答正文。任务记录与队列观测能够核对等待数量、执行耗时、尝试次数、失败数和死信数。测试按需求场景覆盖正常、失败和边界，使用独立数据与可控外部替身，提供一键运行命令及失败退出码。

#### Scenario: 查询一次请求及工具调用
- **GIVEN** 用户执行了一次包含 MCP 调用的编辑请求。
- **WHEN** 开发者按请求标识查询日志。
- **THEN** 能关联请求及工具调用的结果和必要耗时，日志每行可独立解析为 JSON，不包含敏感凭据和私人问答正文。

#### Scenario: 测试发现行为错误
- **GIVEN** 测试环境独立，模型、信源和时间均可控制，账号隔离或去重逻辑被改坏。
- **WHEN** 开发者按文档执行一键测试。
- **THEN** 对应行为测试失败，命令以非零退出码结束，报告指出需求场景，不能以跳过或模拟成功掩盖失败。

#### Scenario: 无外网运行行为测试
- **GIVEN** 测试数据和外部服务替身已准备完成。
- **WHEN** 在没有外网访问的环境运行测试。
- **THEN** 正常、失败及边界场景仍可验证，不依赖真实模型调用或产生模型费用；真实模型效果核验单独记录。

#### Scenario: 提交时间与执行时间分离
- **GIVEN** 使用相同输入规模、真实 API 与队列，以及可控制耗时的模型和信源替身。
- **WHEN** 分别在两档处理耗时下连续提交 20 个不同合法操作，记录每次提交耗时、P95 及处理器完整执行耗时。
- **THEN** 提交响应不含最终结果，P95 显著小于完整执行耗时且不随处理器等待时长同比增长；记录测试阈值、环境和实际样本，不以重复同一操作的去重快路径替代提交测量。

#### Scenario: 异步行为形成可重复证据
- **GIVEN** 异步接口与 Worker 已实现，测试数据库、Redis 和替身均与实际用户数据隔离。
- **WHEN** 运行提交耗时、停止全部消费者、重复提交、重复投递及事务失败的验收用例。
- **THEN** 每条用例保存操作、HTTP 响应、任务状态和必要数据库断言；查询不会触发执行，重复结果与孤儿任务数量可核对，失败返回非零，未执行项目保留未验证。

### Requirement: OPS-05 版本发布与数据恢复

系统 SHALL 按版本或提交标识构建及发布，顺序包含构建、迁移、启动、健康检查与行为验证。发布前保留上一可运行版本和数据库备份，迁移说明恢复方式。初始备份每日一次、保留最近 7 份，恢复目标为最多损失一天数据且两小时内恢复，实际能力以恢复演练记录核验。

#### Scenario: 发布成功与优雅停止
- **GIVEN** 新版本已完成必要验证，上一版本与数据库备份可用。
- **WHEN** 操作者按文档发布并停止旧进程。
- **THEN** 新版本显示对应版本标识并通过健康检查；旧进程停止接收新任务，完成或明确中断在途工作，未完成任务可按任务规则恢复。

#### Scenario: 发布失败后恢复
- **GIVEN** 新版本启动或验证失败，且迁移记录说明了回退对数据的影响。
- **WHEN** 操作者执行文档中的恢复步骤。
- **THEN** 系统恢复到匹配的可运行版本和数据状态，重新验证健康及主要行为，并记录实际恢复耗时和数据恢复点。

#### Scenario: 备份不可读取
- **GIVEN** 选定备份缺失或无法读取。
- **WHEN** 操作者执行恢复检查。
- **THEN** 恢复明确失败，不删除当前数据，不把未经验证的备份记为可恢复，报告可查明的失败原因。
