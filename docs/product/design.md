# NewsClaw 技术设计

## Context

NewsClaw 的产品范围见 [产品范围](README.md)。系统以共享新闻库连接编辑、技能和专题，来源信息必须在检索、回答、时间线及图谱之间保持一致。个人会话、偏好和阅读记录归属用户，公共管理权限与私人数据访问分别判定。

## Goals / Non-Goals

**Goals:**

- 一套内容整理结果服务全站阅读和个人编辑，减少重复采集及模型调用。
- 在明确账号归属的基础上提供持续阅读、记忆更新和专题跟进。
- 采用模块化后端与固定任务，使前端、API、MCP 和后台复用同一业务规则。
- 保留可追溯来源、可观察失败和可复现运行方式。

**Non-Goals:**

- 多租户组织权限、通用工作流与可执行代码插件。
- 独立图数据库、跨领域知识推理和多智能体协作平台。
- 全网热度预测、自建对抗反爬系统及外部消息渠道。

## Decisions

### 1. 应用结构

前端使用 React Router、TypeScript、Tailwind CSS；后端使用 Node.js、Fastify 和 PostgreSQL。API 与后台执行器共享业务模块和镜像，按运行命令启动不同进程。Docker Compose 启动 API、Worker、PostgreSQL 和 Redis。后台使用 BullMQ；先部署一个 Worker 进程和一个业务队列，任务类型区分不同工作，另外保留一个没有自动消费者的死信队列。API 与 Worker 共用业务模块和镜像，不拆成额外的业务服务。Redis 使用持久化卷、AOF 和 `noeviction`，不能按缓存策略淘汰队列数据。AOF 的同步策略与实际恢复范围在运行说明中明确。

代码按账号、新闻与事件、编辑、技能、专题分模块。每个模块保留路由、业务服务和必要的数据访问边界。外部模型、信源解析与 MCP 协议在适配层处理。这个结构让用户请求和后台任务复用同一份规则，服务之间无需额外的网络调用。

### 2. 数据关系

| 对象 | 主要关系与约束 |
| --- | --- |
| 信源与报道 | 报道按信源和规范化 URL 唯一，分别保存发布时间与原文链接；同文可复用正文及派生结果 |
| 事件与图关系 | 一个事件关联多篇报道；实体与关系保存报道依据；事件归属修正后各入口读同一关系 |
| 账号与编辑 | 每个账号一位编辑，编辑配置与私人对象带所属账号标识 |
| 会话与记忆 | 会话拥有独立消息历史；明确兴趣和手动记忆优先于自动整理结果 |
| 技能 | 公共模板与个人副本分别保存，副本记录模板来源但独立修改和启停 |
| 专题与成果 | 专题关联报道、笔记与成果；成果保存生成时正文、技能和来源，分享只引用主动发布的成果快照 |
| 日报与手记 | 按所属账号与业务日期唯一；全站日报使用独立公共归属，不与个人日报混淆 |
| 提醒与任务 | 提醒按用户与新增报道唯一；PostgreSQL 任务记录业务状态、归属、执行次数、结果与错误；待投递记录连接业务事务和 BullMQ |

正文与派生结果共享不合并报道来源。私人笔记和编辑手记不写回公共事件事实，也不作为新闻引用来源。

### 3. 新闻、检索与热点

RSS、公开 API 和网页内容进入统一报道格式。处理依次完成规范化、去重、筛选、摘要、必要翻译和索引。事件聚合使用标题、时间、实体和内容相似度；不确定的报道独立保留，管理员可修正。

关键词与向量检索使用 PostgreSQL 体系，结果均带报道标识及可引用文本。查询合并重复命中并限制返回数量，模型只读取本次相关材料。来源只有摘要时保留内容范围，不生成冒充原文的全文。

热点按最近 24 小时的独立信源数、有效报道数、最近发布时间及事件标识依次排序，保存每日统计用于趋势。此统计表示本站收录内容的近期热度。

### 4. 编辑执行

每次提问组装编辑人设、明确兴趣、相关记忆、当前阅读对象及会话历史；根据问题检索材料，并允许模型通过 MCP 查询新闻或事件。工具调用由服务端校验和执行，结果回传模型继续回答。设置明确的单次调用超时与工具轮次上限，达到上限时说明任务未完成。

接口流式返回文本、来源和必要状态。服务端根据工具和检索结果生成引用映射，禁止模型自行构造来源记录。图谱与双语输出校验结构后呈现。任务失败保留用户输入和已有成功消息，失败回答不作为完整结果供后续引用。

技能显式选择优先，自动选择只在本人启用的技能中选择一项，也允许不使用。技能说明参与本次编辑执行，工具权限仍由服务端决定。

### 5. 个性化与后台任务

个人日报使用兴趣和记忆筛选共享新闻，再生成导读。做梦整理消费上次成功位置之后的新活动，生成手记并补充自动记忆。手记、记忆更新和处理位置在同一事务提交，模型调用在事务外完成；失败后可重新处理同一批活动。

#### 任务范围与触发

| 固定任务 | 触发与作用范围 | 重复及更新语义 |
| --- | --- | --- |
| 采集整理 | 定时采集启用信源；管理员可主动触发某信源采集或重试未完成处理 | 同一次触发的重放复用任务；后续采集批次可以取得新内容，同一信源与规范化 URL 不重复建报道 |
| 全站与个人日报 | 每日调度；用户可重新生成自己的当日日报，管理员管理公共失败任务 | 按公共归属或账号加业务日期唯一；同一次生成的重放不重复生效，主动重新生成使用新的操作标识，成功后更新当天同一份日报 |
| 编辑手记 | 每日调度，根据账号上次成功位置处理新增活动 | 同批重试不重复更新记忆或推进位置；当天有新活动时更新同一份手记，保留已整理内容 |
| 更新提醒 | 新报道入库时，在同一事务中登记待处理任务 | 执行时重新检查有效关注；同一账号与新报道只保存一条提醒，多个关注命中合并 |

定时触发使用现成调度能力。调度触发也调用统一任务接收服务，先落 PostgreSQL，再投递 BullMQ；定时入口中的轻量触发任务不直接执行业务。按类型、对象和计划执行时间生成稳定操作标识，调度重复唤醒不会新建相同操作。编辑连续问答与交互式技能保留 SSE，不统一改成后台任务；重新生成专题成果仍创建新的成果。

#### 接收与查询

任务接收在 API 中完成身份、角色、输入和资源归属检查。主动触发接口在 PostgreSQL 事务提交后返回 `202`，使用统一响应结构，`data` 包含 `taskId`、当前 `status` 和 `statusUrl`，不等待外部调用也不携带新生成的业务结果。`GET /api/v1/tasks/{taskId}` 只读，返回当前状态、必要进度、执行次数、结果引用或可公开的错误；到达成功或最终失败后前端停止轮询。首次响应表示已持久接收，不表示已经入队或完成。

重复请求携带同一操作标识且参数一致时复用原任务，返回其当前状态；相同操作标识但参数不同返回 `409`。操作标识在已认证账号与业务类型内约束，不能通过猜测标识查询其他用户的任务。身份以服务端会话确定，客户端不能指定执行账号。

管理员可查询与重试公共任务；个人任务仅所属用户可查询，管理员不能读取其输入、结果或私人错误详情。个人日报的重新生成通过本人业务接口触发，私人手记与提醒由调度和业务事件触发，不额外增加人工管理页面。未登录返回 `401`，普通用户调用公共任务管理返回 `403`，跨账号与不存在的任务统一返回 `404`。执行前及结果提交前重新检查目标是否存在、归属及适用权限；已删除对象、停用信源或取消关注不能因旧任务继续产生不符合当前合同的写入。

#### 业务记录与队列的分工

PostgreSQL 保存业务任务的 `taskId`、类型、归属、操作标识、输入引用、`pending/running/succeeded/failed`、累计执行次数、当前执行标识、结果引用、错误及创建和起止时间。输入引用固定本次处理所需的报道版本、活动范围或生成参数；同一操作重试不能悄悄变成另一次工作。BullMQ 保存等待、延迟、执行锁等调度细节，不把内部调度结构复制进业务表。消息只带任务标识与投递代次，输入和身份由 Worker 从 PostgreSQL 加载。

任务创建与本次业务写入、待投递记录在同一 PostgreSQL 事务提交。Worker 进程内的投递循环读取待投递记录，使用确定性的 BullMQ `jobId`（任务标识加投递代次）添加消息，成功后标记投递完成；失败保留待投递状态，下轮继续。投递成功而标记前中断可能产生重复消息，接受至少一次投递，由业务执行吸收重复。Redis 不可用不会丢弃已接收任务；PostgreSQL 事务失败则不返回已接收，也不提前投递消息。

同一队列任务成功后，先提交 PostgreSQL 中的业务结果和任务成功状态，再让 BullMQ 完成该次处理。Worker 再次收到已成功任务时直接完成消息，不重做模型调用或业务写入。对仍需执行的任务，在领取时登记新的执行标识；结果提交使用任务标识、投递代次和本次执行标识做条件更新，失去执行资格的旧尝试不能覆盖新尝试。外部调用设置可取消的超时，不在长事务内等待模型。

BullMQ 负责续锁和 stalled 检测。进程退出或失去锁后由它安排重新领取；PostgreSQL 中遗留的 `running` 状态在有效重领时更新，不另造一套独立租约调度器。Worker 恢复时核对非终态任务与 BullMQ 的实际状态：队列任务仍存在时沿用，已失败时收敛业务失败状态，消息已不存在时重新登记投递；不能仅因业务记录显示 `running` 就永久跳过。此恢复同时用于持久化恢复后的缺失消息，不能无条件把所有任务重新入队。

#### 有限重试与死信

模型或信源的网络错误、超时、限流及临时服务故障可有限重试，参数不合法、权限不成立、对象已删除或认证配置无效直接终止。自动尝试上限和外部调用超时在任务策略中明确，采用 BullMQ 的指数退避与抖动；执行次数在开始业务尝试时累计，进程中断后重领也计入，达到上限不能因反复重投继续调用外部服务。BullMQ 的锁恢复上限与业务尝试上限分别记录，不把两者当同一个计数。

可重试失败尚有额度时，业务任务回到 `pending` 并保留最近错误，由 BullMQ 安排重试。不可重试或耗尽上限时，在同一 PostgreSQL 事务中标记 `failed`、保存错误及执行记录，并登记发往死信队列的待投递记录。投递循环将任务标识、失败代次和脱敏失败摘要加入死信队列，投递中断后可继续；不能只依赖一次内存事件。死信队列不自动消费，BullMQ 的 failed 集合与死信队列分别说明，计数不得混同。

管理员通过已有公共任务重试入口处理公共死信，重新检查权限和输入，在同一任务上增加投递代次、保留上一轮失败记录并重新登记投递。人工重放获得新一轮有限自动尝试额度，累计历史次数仍保留；重复点击同一重放请求不能创建多个代次。旧代次消息不再执行业务。私人任务的失败和恢复仍遵守其归属及业务触发规则，死信内容不向管理员暴露私人材料。前端显示可理解的失败，不展示堆栈、内部地址和密钥。

#### 结果去重与并发

任务操作标识避免重复创建同一工作，业务唯一约束保证重复消费不增加重复新闻、日报、手记和提醒。对日报或手记等同一对象的不同合法更新，还需在提交时比较生成版本或活动处理位置：迟到的旧生成结果不能覆盖已提交的新版本，活动位置已经前移时不能重新应用旧记忆。新的生成失败时保留上一份成功结果。

两个消费者可能先后调用模型，即使最终只允许一份结果提交；不承诺外部模型调用恰好一次。验收同时检查数据库结果与实际执行记录，区分“结果不重复”和“没有重复调用”。相同新增报道命中多个关注项时只发一条站内提醒，后续另一篇报道仍能触发提醒。已保存的专题成果保留生成时材料，重新生成产生新的成果。主动分享先预览独立的公开快照，撤销后分享 URL 不再提供内容。

#### 异步验证

三条主要判据使用隔离的数据库、Redis 与可控模型和信源替身，操作真实 API 与 Worker。实施时固定输入规模、处理耗时档位及判定阈值，保留各次测量值。

| 判据 | 前置条件与操作 | 可观测结果 |
| --- | --- | --- |
| 提交不等待业务执行 | 在两档处理耗时下各连续提交 20 个不同合法操作，记录提交耗时与 P95，并直接调用同一处理服务取得完整执行耗时 | 提交返回 `202` 且不含最终结果；P95 显著小于执行耗时，处理等待增加时提交耗时不同比增长；重复操作的去重快路径单独验证 |
| 停止 Worker 后任务仍可恢复 | API 与数据库可用，停止全部 Worker 后提交任务并查询，再恢复 Worker | 任务保持 `pending`；恢复后投递循环自动入队并执行到 `succeeded`，无需重新提交 |
| 重复不产生重复结果 | 对同一操作重复请求，并分别重投消息、在结果提交后确认前终止 Worker 再恢复 | 请求复用任务，业务结果保持唯一；已成功任务不再调用模型，其他重试如实记录实际执行次数 |

接收事务中途失败时核对业务、任务和待投递记录一并回滚；结果提交失败时核对原有成功内容、任务状态与处理位置。另复核查询无副作用、私人任务隔离、有限重试、死信恢复和迟到结果，分别对应运行需求中的场景。

首次手工复现后，将判据固化为 `apitest/cases/` 用例并接入现有 `npm run check` 入口。运行记录写入根目录 `reports/`，包含环境、版本、命令、实际响应、任务状态、数据库断言与结论；并发和事务记录分别使用 `reports/risk-concurrency.md`、`reports/risk-transaction.md`。同时保存队列等待数量、消费耗时、尝试次数和死信数量，并用版本标签关联已验证的交付。当前这些用例与运行报告均待实现后执行。

Redis 持久化及淘汰策略沿用 [BullMQ 运行说明](https://docs.bullmq.io/guide/going-to-production)，重试与失锁恢复分别参考[失败重试](https://docs.bullmq.io/guide/retrying-failing-jobs)和[中断任务恢复](https://docs.bullmq.io/guide/jobs/stalled)。

## Risks / Trade-offs

| 情况 | 处理方式 |
| --- | --- |
| 信源正文不完整或不可达 | 保留实际取得内容、来源与失败状态，既有报道继续可读 |
| 模型输出不准确或结构无效 | 以检索材料限定引用，校验结构；失败明确提示并允许重试 |
| 事件被错误聚合 | 保留每篇报道及来源，管理员修正关联，不删除原始来源记录 |
| 后台重复领取或进程中断 | BullMQ 负责失锁恢复；执行资格、业务唯一约束与短事务保证结果一致，失败任务可重跑 |
| 数据库提交与队列投递之间中断 | 待投递记录恢复入队，重复消息按任务和业务规则处理 |
| Redis 恢复后缺少消息 | 核对非终态任务与队列状态后补投，已成功任务不再执行 |
| 自动偏好与用户填写冲突 | 用户明确内容优先，自动整理仅补充允许更新的记忆 |

## Migration Plan

从空数据库建立结构与约束，先完成可启动骨架及健康检查，再建立身份与任务基础，接通信源采集整理的第一条后台流程后逐组交付其他能力。每组使用固定样本与模型替身验证，最后核验真实模型效果。发布记录使用版本号，数据库结构变更与应用版本相配套；恢复步骤、备份目标及实际验证方法见运维规范。
